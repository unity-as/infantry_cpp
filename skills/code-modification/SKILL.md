# code-modification —— 修改现有代码逻辑

> 修改比新写更容易破坏系统：改动前必须理解现状、评估影响、留基线。
> 行为流程遵循 change-discipline，代码规范遵循 c-coding-standards。

## 1. 先读现状（理解门禁）

- 读完整个函数/模块，先讲清楚：它现在干什么、被谁调用、数据从哪里来到哪里去
- 复述不清楚 = 没懂，不许改
- 不确定框架组织时先读 stm32-framework / ONBOARDING

## 2. 找调用链与影响面

- rg 搜所有调用点
- 接口签名一变，所有调用方都要跟
- 数据契约（Cmd/Feed）一变，相关子系统全要评估
- 改动前画出影响范围，写进方案

## 3. 留基线（可回滚前置）

- 确认 git 状态；没有 git 先建仓或备份
- 记录当前行为基线（现象/日志/输出），改坏了能对比、能回滚

## 4. 方案先行（等用户确认）

- 列出改动方案：改哪个文件、哪几行、改前→改后、为什么
- 用户确认后才动手

## 5. 最小改动

- 一次只改一个逻辑点
- 禁止顺手改格式、命名、无关代码
- 接口变更优先"新增 API 保留旧 API"过渡，不直接改签名

## 6. 展示 diff（等用户过目）

- 写入前展示完整 diff（改前→改后）
- 用户过目后才落地

## 7. 验证与报告

- 编译 + 运行验证，确认 A 没坏
- 报告：改了什么、为什么、验证了什么
- 失败如实报告，不隐藏

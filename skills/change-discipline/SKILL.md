# change-discipline —— AI 变更纪律（总纲）

> 本 skill 是所有项目 skill 的公共底座，其他 skill 都引用本文件的工作流。
> 违反本文件任何一条 = 事故，无论功能是否完成。

## 0. 可回滚前置（最高优先级，动手前的第一道检查）

任何写操作（改代码/改配置/删文件/生成工程）之前，先确认回滚手段存在：

1. 检查 git：仓库存在、当前状态已知（git status / git log）、干净基线已记录；
   没有 git 的目录必须先建仓或手动备份。
2. 留基线：改 A 之前记录基线（RTT 输出快照、关键变量值、可复现行为），
   代码基线 = 当前可工作的版本。
3. 一个任务一个回滚点：每次改动都有对应的提交/备份点，改坏了能一键回到改动前。
4. 删除可恢复优先：移动/改名 > 删除；任何删除先列清单经确认。
5. 不满足以上任何一条 = 禁止动手，先补齐回滚手段再继续。

犯病后的处理顺序：定位违反了哪条 → 回滚到基线 → 把教训修进 skill → 重做。

## 1. 工作流总纲（六步，缺一不可）

理解门禁 → 复用检查 → 方案门禁 → 展示门禁 → 写入 → 验证与报告

**每一步必须输出固定标记。回复里没有标记 = 该门禁没走 = 禁止进入下一步。**

| 门禁 | 固定标记 | 必须输出的东西 |
|---|---|---|
| 理解门禁 | `[理解摘要]` | 这属于哪一层、依赖什么、影响哪些文件 |
| 复用检查 | `[复用检查]` | 搜了哪些路径、找到什么、为什么不用（或确认没有） |
| 方案门禁 | `[方案清单]` + `[方案确认] 请确认` | 文件/内容/原因/影响面，等用户确认 |
| 展示门禁 | `[DIFF]` | 完整 diff/代码块，用户过目后才落地 |
| 验证报告 | `[验证报告]` | 基线 + 验证结果，逐项对比 |

## 1.5 执行机制（写了的必须做，否则等于没写）

规则写在文档里没有任何意义，执行才是一切。执行靠机制，不靠自觉：

1. **门禁标记**：每一道门禁必须输出上表对应的固定标记。回复里没有标记 = 该门禁没走 = 禁止进入下一步。
2. **流程自检块**：每一轮回复结尾必须输出：
   ```
   [流程自检] 理解✅/❌ 复用✅/❌ 方案✅/❌ 展示✅/❌ 写入✅/❌ 验证✅/❌
   跳过项及原因：……
   ```
   没做就标 ❌，禁止假装 ✅。
3. **确认门禁卡住工具调用**：写文件、编译、删除等任何有副作用的工具调用，必须先在本轮回复输出 `[方案确认] 请确认`，且用户明确回复确认后，才允许调用工具。没有确认 = 不调用。
4. **一步一停**：一轮只做一步，做完必须停。出现"读 + 改 + 编译"连续操作 = 违规，立即停止并回滚。
5. **违规处理**：用户指出跳步/未确认操作时，立即停止；报告违反了哪一条；回滚已做的操作；把教训写回本文件。

## 2. 理解门禁

动手前先复述：这个改动属于哪一层（application/modules/bsp/HAL）？依赖什么？影响哪些文件？
复述不清楚 = 没懂，不许继续。

输出格式：
```
[理解摘要] 层：…；依赖：…；影响文件：…
```

- 不确定框架怎么组织时，先读 stm32-framework 和 ONBOARDING.md，不要猜。
- 禁止不懂装懂：不确定就问用户，不假装理解。
- 区分事实 / 推断 / 假设：每个关键判断标注来源，禁止把推断当结论。

## 3. 复用检查

写任何代码前先搜索代码库（D:\MyTrain\robomaster、D:\MyTrain\kit\DRIVER 等），
用 rg 搜索同功能实现。

输出格式：
```
[复用检查] 搜索路径：…；找到：…；结论：复用/重写（理由）
```

- 找到现成实现（模块/函数/注册模式）→ 必须复用或扩展，禁止重写。
- 确实没有 → 报告搜索过的位置，经用户确认后才允许新写。
- 常见漏搜：DRIVER 库、旧工程的 modules、bsp 封装（用 bsp_pwm 而不是手写 TIM）。

## 4. 方案门禁

任何改动先列清单（文件/内容/原因/影响面），等用户确认后才动手。

输出格式：
```
[方案清单] 文件：…；内容：…；原因：…；影响面：…
[方案确认] 请确认
```

【包含外部命令】CubeMX 生成、烧录、清理、运行脚本等同属此门禁。
卡住/超时先报告，禁止自行扩大操作范围。

【执行约束】用户未明确回复确认前，禁止调用任何写文件、编译、删除等有副作用的工具。

【豁免】用户明确说"这次不用 xx / 直接做"时，可以跳过对应门禁，
但必须在回复中明说跳过了什么。

## 5. 展示门禁

写入文件之前，必须先展示完整代码或 diff，用户过目后才落地。

输出格式：
```
[DIFF] 改前 → 改后（完整代码块）
```

- 禁止"边写边入库"、"写完才说"。
- 禁止未经用户看过代码就写入文件。

## 6. 安全红线

- 注册≠启动：危险外设默认不输出，Enable/Start 必须显式。
- 保护阈值与检查不得削弱（超温/过流/看门狗）。
- 断点冻结风险：功率输出期间 halt 有烧毁风险。
- 先确认供电前提：功率/温度上不去先查供电，不先怀疑代码。

## 7. 删除纪律

- 删除前必须列出完整清单（路径/内容/影响）经确认。
- 禁止递归删除（禁止 rm -rf 类宽泛命令）。
- 清理默认移动/改名，不是删除。
- 删除后报告：删了什么、是否可恢复。
- 删除/重构时检查：被删实现承载的功能，代码是否保留在正确层级
  （如删 bsp_bmi088 时，bmi088 驱动在 modules 层保留，不因删错误实现而丢功能）

## 8. 验证与报告

- 改 A 前留基线，改 B 后验证 A 没坏。
- 一次只做一个任务，不混改；每个改动可回滚。
- 不隐藏失败：改完发现不工作，如实报告现象和证据，不掩盖、不删日志。

输出格式：
```
[验证报告] 基线：…；编译：…；逐项核对：…；结果：…
```
